# Safari (macOS + iOS) build

The same `dist/` MV3 bundle that ships to Chrome and Firefox is wrapped
in an Xcode project so it can be installed as a Safari Web Extension on
macOS and iOS. The wrapper includes a **native messaging host** for
future Keychain reads/writes. Current JS-side storage still uses the
shared extension `nsecStore`, which now writes new identities as
password-encrypted records by default.

## Status

- Xcode project: **generated and tracked** (`safari/Deepmarks/`).
- Native Keychain bridge: **ported to the modern Safari Web Extension
  API** (`Shared (Extension)/SafariWebExtensionHandler.swift`).
- macOS entitlements: **wired** for Keychain Sharing
  (`org.deepmarks.extension.keychain`) on both the App and Extension
  targets.
- iOS entitlements: **TODO** — Xcode auto-creates these when you add
  the Keychain Sharing capability via the Signing & Capabilities tab.
- App-Store-safe build flag: **wired** (`VITE_APPLE_BUILD=1`,
  consumed by `src/lib/build-flags.ts`). Strips lifetime-upgrade and
  archive-purchase surfaces at minification time so Apple's IAP
  guideline (3.1.1) doesn't reject the submission. NWC stays for
  outbound zaps.
- TypeScript-side `KeychainNsecStore`: **TODO** (v1.1.0). The extension
  JS still uses `browser.storage.local` on Safari like Chrome/Firefox,
  but new records are password-encrypted before the first write.

## One-time per dev machine

1. Install Xcode 15+ (for iOS 17 / macOS 14 minimum, which is also
   what `content_scripts.world: 'MAIN'` and the modern data-collection
   declaration require).
2. Have an Apple Developer account ($99/yr) — required to ship to
   either App Store **and** to test on a real iOS device.

## Regenerate the Xcode project (only if needed)

The project is already in source control. Regenerate **only** when the
extension's manifest, icons, or background topology change in a way
that breaks the existing project structure. Custom changes to
`SafariWebExtensionHandler.swift`, the entitlements files, or the
Xcode project settings will be lost — restore from git afterward.

```bash
cd browser-extension
npm install
npm run build:safari-app       # produces dist/ with payment surfaces stripped

xcrun safari-web-extension-converter dist/ \
  --project-location safari/ \
  --bundle-identifier org.deepmarks.extension \
  --app-name Deepmarks \
  --copy-resources \
  --swift \
  --no-open \
  --no-prompt \
  --force                       # only when actually overwriting
```

## Update the bundled MV3 resources without regenerating

Most of the time you just want to drop the latest `dist/` into the
existing project. One command does both build + sync:

```bash
npm run package:safari-app
```

That first syncs every Safari Xcode target's version from
`browser-extension/package.json`, then runs `build:safari-app` to
produce the App-Store-safe variant in `dist/`, then rsyncs it into
`safari/Deepmarks/Shared (Extension)/Resources/` (the folder Safari
serves to the extension at runtime). `npm run package:verify` checks
Chrome, Firefox, and Safari package versions together. If App Store
Connect needs a distinct build number for a resubmission, run with
`SAFARI_BUILD_NUMBER=...`; the public marketing version still stays
locked to `package.json`. After that, just `Product → Run` in Xcode.

## iOS: enable Keychain Sharing (one-time, in Xcode)

Apple's converter scaffolds the macOS entitlements but leaves iOS
empty. To match macOS:

1. Open `safari/Deepmarks/Deepmarks.xcodeproj` in Xcode.
2. Select the **iOS (Extension)** target → Signing & Capabilities → +
   Capability → **Keychain Sharing**. Add the group
   `org.deepmarks.extension.keychain`.
3. Repeat for the **iOS (App)** target with the same group.
4. Set the team for all four targets (iOS App, iOS Extension, macOS
   App, macOS Extension) to your Apple Developer team.

Once added, Xcode creates `iOS (Extension)/Deepmarks.entitlements` and
`iOS (App)/Deepmarks.entitlements` automatically. Commit those.

## Build & run

```
Xcode → Product → Run (⌘R)                         # macOS host app, includes the extension
Xcode → Product → Destination → iOS Simulator → Run # iOS host
```

On macOS: open Safari → Settings → Extensions → enable **Deepmarks**.
On iOS Simulator: Settings → Safari → Extensions → enable **Deepmarks**.

## Distribution

```
# macOS Mac App Store
Product → Archive → Distribute App → Mac App Store Connect

# iOS App Store
Switch scheme to iOS → Product → Archive → Distribute App → App Store Connect
```

Apple review: ~1–3 days for a new extension, often <24h for updates.
Expect questions about:
- Broad `host_permissions: ['https://*/*']` — same answer as Chrome/Firefox: only at user-initiated save.
- Nostr recovery-key storage — new Safari extension identities are password-encrypted in extension storage today; Keychain/biometric storage is the next native bridge step.
- Lightning archive and lifetime purchases are stripped from Apple builds for non-lifetime users via `VITE_APPLE_BUILD=1`. Existing lifetime archive access remains because no in-app purchase is shown.

## Threat model recap

| Platform | nsec storage | Encryption |
|---|---|---|
| Chrome / Firefox | `browser.storage.local` encrypted record by default; legacy plaintext records are migrated on popup boot | extension password → PBKDF2-SHA-256 (600k) → AES-256-GCM |
| **Safari macOS** (current JS path) | same encrypted `browser.storage.local` record as Chrome/Firefox | extension password → PBKDF2-SHA-256 (600k) → AES-256-GCM |
| **Safari iOS** (after JS-side Keychain wiring) | **Keychain + Secure Enclave** | **OS-managed**, biometric-gated read |

Same `lib/nsec-store.ts` facade abstracts both. On Safari it'll route
`get/set/clear` through `browser.runtime.sendNativeMessage` to the
native handler in `Shared (Extension)/SafariWebExtensionHandler.swift`.
On other browsers it stays in `browser.storage.local` with the
extension-password-derived key wrap.

## Native message protocol

The handler listens for messages of this shape:

```jsonc
// JS:  browser.runtime.sendNativeMessage({ op: 'get' })
//   →  { ok: true, account?: { schemaVersion, nsecHex, pubkey, signedInAt } }

// JS:  browser.runtime.sendNativeMessage({ op: 'set', account: { ... } })
//   →  { ok: true }

// JS:  browser.runtime.sendNativeMessage({ op: 'clear' })
//   →  { ok: true }

// On any error:
//   →  { ok: false, error: '<reason>' }
```

The keychain item identity is fixed: service `org.deepmarks.extension`,
account `nsec`, access group `org.deepmarks.extension.keychain`,
accessibility `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`.
Single-account per browser profile for now; if account switching ever
ships in the extension, the handler grows a `key` field to dedup.
