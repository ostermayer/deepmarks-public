# iOS Xcode setup — share extension native publish

The native sign-and-POST path is checked into the iOS project. No
manual Xcode package edits are required for a normal build.

Important files:

- `frontend/ios/App/KeychainSharedStore.swift`
- `frontend/ios/App/NostrEvent.swift`
- `frontend/ios/App/NostrPublish.swift`
- `frontend/ios/App/App/SharedNsecPlugin.swift`
- `frontend/ios/App/Secp256k1Schnorr/Package.swift`

`CapApp-SPM/Package.swift` is generated by Capacitor. Do not edit it.
The project links `GigaBitcoin/secp256k1.swift` v0.23.x directly and
uses the local `Secp256k1Schnorr` package only to enable the package's
`schnorrsig` feature. The product linked to both `Deepmarks` and
`DeepmarksShare` is `libsecp256k1`.

## Build from Xcode

If web assets changed, sync Capacitor first:

```bash
cd /Users/dan/deepmarks/frontend
npm run build:apple
npx cap sync ios
```

Then open:

```bash
open /Users/dan/deepmarks/frontend/ios/App/App.xcworkspace
```

In Xcode, select either the `Deepmarks` or `DeepmarksShare` scheme and
build for an iOS simulator or a signed device. Both targets include the
shared signing files and `libsecp256k1`.

Command-line build smoke test:

```bash
cd /Users/dan/deepmarks/frontend/ios/App
xcodebuild -project App.xcodeproj \
  -scheme DeepmarksShare \
  -configuration Debug \
  -destination 'generic/platform=iOS Simulator' \
  CODE_SIGNING_ALLOWED=NO \
  build
```

If Xcode package resolution gets stale, use **File → Packages → Reset
Package Caches**, then build again. Do not move the dependency into
`CapApp-SPM/Package.swift`; `cap sync` owns that file.

## Runtime: how it works end-to-end

1. User signs in (any signer that exposes a raw nsec — local nsec,
   nsec-restored-from-recovery, etc.). `frontend/src/lib/stores/
   session.ts:writeStoredNsec` mirrors the nsec into the shared
   Keychain via the `SharedNsec` Capacitor plugin.
2. User shares a URL → the DeepmarksShare extension opens.
3. User picks **Public** in the visibility control and taps **Save**.
4. The extension reads the nsec from the shared Keychain, builds +
   signs a kind:39701 event with NostrSigner, builds a NIP-98
   `Authorization` header, and POSTs `/publish`.
5. On 2xx, the extension stamps the AppGroup pending-share record
   with `published: "1"` and dismisses immediately — no host-app
   foreground required.
6. On failure (no nsec, offline, server reject), the extension
   falls back to the existing host-app-open flow. AppGroup already
   has the share, so the JS-side share-drain picks it up on next
   foreground and publishes via POST `/publish` from there.
7. On next foreground, JS share-drain reads the AppGroup queue.
   For entries with `published: "1"` it skips the duplicate `/publish`
   POST and just calls `rememberOwnBookmark` to render the bookmark in
   the user's local list.

Private bookmarks (visibility = "private") always take the host-app
path because they need a NIP-44 chunked-set rewrite that isn't
implemented natively yet. Default-visibility shares also take the
host-app path so the JS-side user setting decides public vs private.
